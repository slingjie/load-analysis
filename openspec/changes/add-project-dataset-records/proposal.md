# 变更提案：新增“项目级数据集保存与复用”（本地优先，后续可迁移 Supabase）

## 背景与目标
- 背景：当前系统的负荷数据仅在浏览器内存中保存；刷新页面或再次进入后需要重新上传文件并重复测算，影响测试效率与可追溯性。
- 目标：新增“项目级”的负荷数据集保存能力，使用户可在不同页面/不同会话中直接引用已保存的数据集进行测算，无需重复上传。
- 交付策略：先实现“本地保存/复用”（单机可用、无登录、离线可用），后续再按需迁移到 Supabase（跨设备、可上云）。
- 未来部署约束（后续阶段）：前端计划部署到 Cloudflare（静态站点），数据库/存储计划使用 Supabase（Postgres + Storage + Auth）。

## 现状摘要（与本提案相关）
- 前端 `App.tsx` 存在“全局上传负荷”的内存状态（`loadCleanedData/loadMeta/loadQuality`），可被 `StorageCyclesPage` 复用。
- 后端清洗接口 `/api/load/analyze` 返回 `cleaned_points`（`timestamp + load_kwh`），前端可直接用于渲染与后续计算。
- 后端储能测算接口支持在 `payload.points` 传入点位数组（无需再次上传文件），具备“复用点位”的技术基础。

## 变更范围
- 前端
  - 第一阶段：本地持久化（IndexedDB 优先；必要时降级到 localStorage），支持项目/数据集保存、加载、选择与复用测算。
  - 第二阶段：增加 Supabase 集成（Auth + 数据表 + Storage），实现跨设备同步与迁移。
  - 新增“项目/数据集”管理能力：创建项目、保存数据集、列出/选择数据集、加载数据集到全局状态。
  - 在现有测算流程中支持“引用已保存数据集”进行计算（优先走 `payload.points`）。
- 数据库（Supabase，第二阶段）
  - 建议增加 `projects / datasets / runs` 三类资源（见设计文档与规格），并开启 RLS，默认按用户隔离数据。

## 非目标
- 不在本次变更中实现“多人协作共享项目/数据集”（可作为后续增强）。
- 不强制将所有后端导出报表迁移到 Supabase Storage（本次优先保证输入数据可复用；结果归档可选）。

## 里程碑（建议）
1) D+0：确认“本地项目/数据集”的最小字段与保存格式（点位序列化方案）。
2) D+2：完成本地保存/加载/选择；打通 StorageCycles 走 `payload.points` 的复用链路。
3) D+4：补齐本地体验（重命名/删除/导入导出/失败降级）与文档。
4) D+?（第二阶段）：完成 Supabase 端表结构 + RLS + 前端接入，并提供“本地→Supabase”迁移入口。

## 待澄清问题（需要你确认）
1) 第一阶段是否允许完全不登录（纯本地）？（推荐：允许）
2) 第二阶段是否需要“登录”与“多用户隔离”？（推荐：Supabase Auth + RLS，默认每个用户私有）
2) “项目”粒度如何定义：按客户/站点/一次方案？是否允许一个项目包含多个数据集与多次测算记录？
3) 需要保存的内容范围：
   - 仅保存“输入负荷数据集”（最小闭环），还是也要保存“测算参数快照/结果摘要/导出文件”？
4) 数据集大小：典型文件多大、点数规模（例如 15 分钟全年约 35040 点）？是否需要压缩存储与去重？
5) 数据隐私要求：是否允许“分享链接/公开只读”？若不需要，本次默认不做共享。
