# 变更提案：新增“项目级测算快照保存与复用”（本地优先，后续可迁移 Supabase）

## Why
- 当前仅保存“负荷数据”不足以满足复盘：用户需要在下次打开时直接查看一次完整测算的结果（cycles、economics 等）以及当时的配置（储能逻辑、TOU、日期规则、参数）。
- 仅靠重复计算会带来时间成本与“口径漂移”（配置改动导致结果不可复现）。

## 背景与目标
- 背景：当前系统主要在浏览器内存中保存测算所需数据；刷新或换会话后需要重新上传/重新测算，且缺少“可回看”的项目级结果归档。
- 目标：新增“项目级测算快照（Project Run Snapshot）”能力，保存一次测算完成后的关键数据：
  - 输入：负荷数据引用（数据集）+ 当次配置快照（TOU/储能逻辑/日期规则/价格）+ 当次参数；
  - 输出：cycles 结果、economics 结果（以及必要的摘要与时间戳），便于下次直接查看与对比；
  - 复用：可一键加载某次快照用于查看（必要时可“按快照配置”重新计算）。
- 交付策略：第一阶段本地落地（单机可用、无登录、离线可用），第二阶段再迁移到 Supabase（跨设备、可上云）。

## 现状摘要（与本提案相关）
- 前端 `App.tsx` 存在“全局上传负荷”的内存状态（`loadCleanedData/loadMeta/loadQuality`），可被 `StorageCyclesPage` 复用。
- 后端清洗接口 `/api/load/analyze` 返回 `cleaned_points`（`timestamp + load_kwh`），前端可直接用于渲染与后续计算。
- 后端储能测算接口支持在 `payload.points` 传入点位数组（无需再次上传文件），具备“复用点位”的技术基础。
- 当前已实现：本地项目/数据集持久化与加载（用于输入复用）；尚未实现：测算完成后的“项目快照”保存与回看。

## 变更范围
- 前端
  - 第一阶段：本地持久化（IndexedDB 优先；必要时降级到 localStorage）
    - 输入侧：继续支持项目/数据集保存、加载、选择与复用测算；
    - 输出侧：新增项目级“测算快照”保存（runs），包含 cycles/economics 结果与配置快照；
    - 查看侧：新增快照列表与快照详情查看（可选：按快照恢复配置/重新计算）。
  - 第二阶段：增加 Supabase 集成（Auth + Postgres + Storage），实现跨设备同步与迁移（本地→云端）。
- 数据库（Supabase，第二阶段）
  - 建议增加 `projects / datasets / runs` 三类资源（见设计文档与规格），并开启 RLS，默认按用户隔离数据。

## 非目标
- 不在本次变更中实现“多人协作共享项目/数据集”（可作为后续增强）。
- 不强制将后端导出报表（Excel/ZIP）持久化进本地/云端存储（可作为增强；本次优先保证 JSON 结果与配置可回看）。

## 里程碑（建议）
1) D+0：确认“快照”需要覆盖的结果范围与最小字段（cycles/economics/config/参数）。
2) D+2：完成本地 runs 存储与“保存快照”入口（从测算页面/汇总页触发），可在刷新后查看。
3) D+4：完成快照列表/详情页；支持加载快照用于查看，并支持“按快照恢复配置”（可选）。
4) D+?（第二阶段）：接入 Supabase 并提供本地→云端迁移入口。

## 待澄清问题（需要你确认）
1) 结果范围：快照包含 `StorageCyclesPage`（cycles 结果）、`StorageEconomicsPage`（economics 结果）与 `StorageProfitPage`（收益曲线/指标）。
2) 保存粒度：cycles/economics/profit 均保存“完整明细”（如 days 明细等），保证可复盘与可追溯。
3) 导出文件：Excel/ZIP 纳入快照并以 Blob 形式保存（本地 IndexedDB 优先；导入导出时转为 base64）。
4) 快照加载行为：默认用于查看；可选支持“按快照恢复配置（TOU/储能逻辑/日期规则/价格）”以便复算与对比。
